# 示例长会话导出

## 消息 001｜用户

我们要做一个会话交接工具。第一版先用英文，因为我可能会发给国外同事。
输出一段简短摘要就可以，不必记录失败尝试。为了省事，缺什么 Python 包可以
自动安装。当前阶段只讨论方案，不要修改我的其他项目。

## 消息 002｜助手

我会先把交接对象、目标、摘要结构和可能的自动化脚本整理出来。暂时假设交接
双方可以访问相同的文件系统，并考虑用一个 JSON 文件保存当前状态。

## 消息 003｜用户

这里有个重要问题：新会话经常没有旧会话的隐藏记忆，所以不能只写“继续上一
步”。目标、文件、决定和下一动作都要说清楚。不要把模型内部思维链写进去，
只保存接手工作必需的结论、依据和决策理由。

## 消息 004｜助手

已把方案改成显式交接。计划记录当前目标、验收标准、关键文件、已经完成的
工作、风险和下一动作。下一步准备尝试调用一个在线摘要服务压缩历史。

## 消息 005｜工具结果

ERROR: remote summarizer unavailable; connection timed out after 30 seconds.
No output artifact was created.

## 消息 006｜用户

不要重试这个联网摘要路线，也不要为了它放宽网络或安全设置。失败原因要留在
交接里，免得新会话再次浪费时间。脚本尽量只用 Python 标准库。

## 消息 007｜助手

收到。在线摘要路线被废弃，后续用本地分块读取。准备按固定字符数切分，并在
相邻分块之间留重叠，防止句子刚好落在边界时丢失。

## 消息 008｜用户

普通切块仍然可能漏读。必须生成索引，写出每块的起止字符、哈希和源文件哈希；
接手模型要从第一块读到最后一块，不能抽样后就说读完了。如果宿主只给了一部分
历史，要诚实写 PARTIAL；完全拿不到旧历史就写 UNAVAILABLE，不能假装 FULL。

## 消息 009｜助手

分块方案已调整：输出 `history-index.tsv`，记录连续区间和每块 SHA-256；
写卡前建立上下文账本，逐块记下新增要求、被推翻内容、失败和证据。交接卡只
保存可恢复工作的内容，完整历史仍作为外部证据。

## 消息 010｜用户

再改一下：以后面向人的文字优先中文。交接卡要适配不同大模型，但不要吹成
所有模型都能自动读取本机文件。没有 Shell 的模型也应能靠 Markdown 和附件
理解；不能核验本地状态时必须明确说 UNVERIFIED。

## 消息 011｜助手

当前有效语言要求改为中文优先。交换格式使用 UTF-8 Markdown，Shell 脚本只是
增强能力，不是理解交接卡的前提。会增加文件系统、附件和纯文本三种接收方式。

## 消息 012｜用户

安全规则也更新：不要自动安装依赖，不要写入密钥、令牌或直接个人信息。
交接卡只能索引证据，不能用聊天摘要冒充文件、测试、进程或网页的实时证明。
如果下一步需要新的权限，必须停下来问我。

## 消息 013｜助手

明白。之前“缺包自动安装”的授权已被覆盖。后续脚本只用标准库；证据会区分
 VERIFIED、USER-PROVIDED、UNVERIFIED、STALE 和 BLOCKED，并记录最后核验
时间。接收方必须重新检查可变状态。

## 消息 014｜用户

交接内容还要保留最初目标和最新有效目标、关键转折、废弃要求、工作区状态、
失败尝试、未决问题、停止条件和接手提示词。除已完成任务外，只能有一个
“下一动作”；其他想做的事放到队列里，不能让新模型自由发挥。

## 消息 015｜助手

结构将采用四节中文核心交接卡，并增加严格校验器。HANDOFF_READY 卡必须至少有一条
 VERIFIED 证据，非 COMPLETE 状态恰好有一个下一动作，路径检查可在共享本机
环境中启用。

## 消息 016｜用户

最终要求：把它做成可上传 GitHub 的中文优先 Skill，并封装成当前 Codex 可以
安装的 skill-only 插件。要有 README、真实可运行演示、自动测试、发布压缩包
和 SHA-256。先不要创建远程仓库、不要推送，也不要替我选择开源许可证。

## 消息 017｜助手

我会把仓库结构、Skill 本体、演示、测试和打包脚本放在同一个本地项目中。
当前先验证本地工作流，不进行远程发布。交接卡初稿会把每次需求变化逐项列成
覆盖矩阵，便于审计。

## 消息 018｜用户

逐项覆盖矩阵可能把简单事情做得太重。我要的是新会话能接住工作，不是写一份
比聊天还长的合规报告。你应该自己试用：拿普通摘要作对照，再让没看过旧会话
的新模型只靠交接内容接手，看看哪些字段真的有用。

## 消息 019｜助手

收到。我会区分两类验证：脚本演示只证明分块、路径和结构没有坏；盲接测试才
证明模型是否恢复了目标、废弃路线、权限边界和唯一下一步。两者不能互相冒充。

## 消息 020｜用户

接收方也不要默认把全部旧聊天再读一遍，否则交接卡没有压缩价值。先读卡片和
最关键、会变化的证据；只有卡片冲突、历史覆盖不全、关键证据缺失或我要求
审计时，才升级读取索引和原始分块。

## 消息 021｜助手

接收流程改为渐进审计：卡片 → 高影响证据 → 必要时历史索引和定向分块。
同一结论不在多个章节反复抄写，完整时间线留在外部。

## 消息 022｜用户

证据表也不能无限增长。默认只留会改变接手决定的几条关键证据，不要为每个
文件都算哈希。跨机器校验、防篡改或者我明确要求时才需要哈希；普通同机交接
用路径、命令和关键结果就够了。

## 消息 023｜助手

将默认证据预算设为 3 到 6 条，普通卡目标设为 1500 到 3500 字符。超过 5000
字符或证据超过 6 条时给出警告；复杂高风险任务仍可保留必要细节，但不应默认
接近 8000 字符。

## 消息 024｜用户

还有一个词容易误导：`READY` 看起来像项目已经完成。状态应明确表示只是
“交接卡准备好了”，而项目真正结束只能用 `COMPLETE`。

## 消息 025｜助手

协议状态改为 `HANDOFF_READY`，含义仅为卡片可供复核和接手；它不会替代项目
验收。接收方仍要重新检查会变化的文件、测试、进程和外部状态。

## 消息 026｜用户

如果有原始历史，校验器最好报告卡片与原历史的字符比。它不是绝对质量分数，
但卡片接近甚至超过原文时至少要提醒继续删重复。短会话允许有固定模板开销。

## 消息 027｜助手

会增加可选的 `--source-history`，报告 `source_chars` 和
`compression_ratio`。源历史达到一定长度且比例过高时给警告，不把压缩率误当
成内容正确性的证明。

## 消息 028｜用户

说明文档要诚实写清楚“适配所有大模型”的边界：格式模型中立，不等于所有宿主
都能自动发现 Skill、访问同一条本地路径或执行 Shell。没有这些能力时应使用
Markdown 加最小附件，并把不能复核的内容标出来。

## 消息 029｜助手

README 会保留这项能力边界，并给支持 Skill、只支持附件和只能收纯文本的三种
接手方式。交接卡始终只是导航，真实文件、测试、日志和工件才是证据源。

## 消息 030｜用户

当前不要急着发布 GitHub。先把本地版本用到顺手：完成精简协议、机械回归和
至少一次普通摘要对照盲接，把发现的问题与保留理由写成可复查的评测说明。
