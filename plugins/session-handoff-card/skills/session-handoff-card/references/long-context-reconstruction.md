# 长上下文重建

仅在历史导出较长、无法一次读取或完整性不确定时使用。

## 写出方

1. 盘点所有可取得来源并记录边界。
2. 对 UTF-8 文本、Markdown、JSON 或 JSONL 运行：

   ```text
   python scripts/chunk_history.py --input <历史文件> --output-dir <分块目录>
   python scripts/verify_history.py --source <历史文件> --index <分块目录/history-index.tsv>
   ```

3. 按索引从第一块读到最后一块。重叠区只用于防止边界丢句。
4. 逐块临时记录新增要求、覆盖关系、失败路线、权限、证据和未决事项。
5. 合并后对照项目证据，生成核心交接卡。

不得抽样代替全量读取。宿主只提供部分历史时使用 `PARTIAL`；完全无法取得必要
历史时使用 `UNAVAILABLE + BLOCKED`。

## 压缩原则

- 交接卡保留当前结论和影响接手的转折，不复制聊天原文。
- 低频时间线和逐块笔记需要时放入外部上下文账本。
- 卡片通常应短于原始历史；超过 8000 字符时先删除重复说明，再外置细节。
- 权限、停止条件、失败且勿重试路线不得因压缩丢失。

## 接收方

先运行结构校验并核验当前证据。若卡片为 `HANDOFF_READY/FULL` 且没有冲突，默认不把
全部历史重新装入模型上下文。需要审计时，先用 `verify_history.py` 检查分块
完整性，再定向读取与冲突或缺口有关的分块；用户明确要求全量审计时才全部读完。
