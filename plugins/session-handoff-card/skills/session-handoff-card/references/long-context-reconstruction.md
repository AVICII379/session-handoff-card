# 长上下文重建

只在历史无法一次读完或完整性不确定时使用本流程。

1. 结构化导出先用 `normalize_history.py` 转为按序编号的 Markdown。支持 ChatGPT
   `mapping` 导出、Claude `chat_messages`、常见 `role/content` JSON、JSONL 和纯文本。
   Gemini、Codex、DeepSeek、通义千问等平台若导出为常见 `role/content` 结构，可用
   `generic`；未知私有结构不应声称已支持。
   归一化不会脱敏或删减消息，输出应留在本地并按原始历史同等级保护，不要直接提交仓库
   或作为默认接手附件。
2. 用 `chunk_history.py` 连续分块。索引保存源文件哈希、每块哈希和精确字符区间。
3. 用 `verify_history.py` 验证首尾相接、无重叠、无缺口、块内容与源文本完全一致。
4. 按消息顺序抽取：当前有效要求、被覆盖要求、决定、失败路线、权限边界、证据、未决项。
5. 后出现的明确要求覆盖早期冲突要求，但旧要求仍应以“失效/不要做”保留，防止复活。
6. 把完整时间线和低影响细节留在历史分块；核心卡只保留会改变接手决定的信息。

抽样只能用于预览，不能产生 `FULL`。如果导出本身可能截断，在卡片中写明这是平台导出的
全部可见内容，而不是账号的全部历史。
